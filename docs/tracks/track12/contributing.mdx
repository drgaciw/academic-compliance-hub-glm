## Getting Started

### 1. Fork and Clone

```bash
# 1. Fork the repository
# Click "Fork" on GitHub

# 2. Clone your fork
git clone https://github.com/YOUR_USERNAME/athletic-academics-hub.git
cd athletic-academics-hub

# 3. Add upstream remote
git remote add upstream https://github.com/ORG/athletic-academics-hub.git
```

### 2. Install Dependencies

```bash
# Install dependencies
pnpm install

# Setup database
pnpm db:generate
pnpm db:push
```

### 3. Configure Environment

```bash
# Copy environment template
cp .env.example .env.local

# Edit with your configuration
# Set DATABASE_URL, API keys, etc.
```

### 4. Run Development Server

```bash
# Start all services
pnpm dev

# Or specific app
pnpm dev:main
```

## Code of Conduct

## Development Workflow

### Branching Strategy

We use a simplified Git flow:

```
main              → Production, always deployable
  ├─ feature/*   → New features
  ├─ bugfix/*     → Bug fixes
  ├─ hotfix/*     → Urgent production fixes
  └─ refactor/*    → Code refactoring
```

### Creating a Branch

```bash
# Update main
git checkout main
git pull upstream main

# Create feature branch
git checkout -b feature/your-feature-name

# Or bugfix
git checkout -b bugfix/your-bugfix-name

# Or hotfix
git checkout -b hotfix/urgent-issue
```

### Commit Guidelines

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```bash
# Format: type(scope): description

# Types: feat, fix, docs, style, refactor, test, chore

# Examples:
git commit -m "feat(auth): add OAuth login"
git commit -m "fix(users): resolve email validation issue"
git commit -m "docs(readme): update installation instructions"
```

### Commit Checklist

Before committing:

- [ ] Code passes linting: `pnpm lint`
- [ ] Type checking passes: `pnpm type-check`
- [ ] Tests pass: `pnpm test`
- [ ] Documentation updated (if needed)
- [ ] Changes are minimal and focused

## Coding Standards

### TypeScript

We use TypeScript for type safety:

```typescript
// ✅ Good: Explicit types
interface User {
  id: string;
  name: string;
  email: string;
}

function getUser(id: string): Promise<User> {
  return prisma.user.findUnique({ where: { id } });
}

// ❌ Bad: Any types
function getUser(id: any): Promise<any> {
  return prisma.user.findUnique({ where: { id } });
}
```

### React Patterns

Use functional components with hooks:

```typescript
// ✅ Good: Functional component
export function UserProfile({ user }: { user: User }) {
  const [expanded, setExpanded] = useState(false);

  return (
    <div>
      <h3>{user.name}</h3>
      {expanded && <p>{user.email}</p>}
      <button onClick={() => setExpanded(!expanded)}>
        Toggle
      </button>
    </div>
  );
}

// ❌ Bad: Class component (avoid)
export class UserProfile extends React.Component {
  // ...
}
```

### Naming Conventions

```
Files:      kebab-case     (user-profile.tsx)
Components: PascalCase      (UserProfile.tsx)
Functions:  camelCase       (getUserProfile)
Variables:  camelCase       (userName)
Constants:  SCREAMING_SNAKE_CASE (MAX_USERS)
Interfaces:  PascalCase      (UserProfile)
Types:      PascalCase      (UserRole)
```

### File Organization

```
feature/
├── components/           # Feature-specific components
│   ├── UserProfile.tsx
│   └── index.ts
├── hooks/               # Feature-specific hooks
│   └── useUserProfile.ts
├── api/                 # API routes
│   └── route.ts
├── lib/                 # Utilities and helpers
│   └── utils.ts
├── types/               # TypeScript types
│   └── index.ts
└── index.ts             # Public API
```

### Error Handling

Use consistent error patterns:

```typescript
// ✅ Good: Custom error class
class ValidationError extends Error {
  constructor(
    public field: string,
    message: string,
  ) {
    super(message);
    this.name = "ValidationError";
  }
}

try {
  validateUser(user);
} catch (error) {
  if (error instanceof ValidationError) {
    return NextResponse.json({ error: error.message }, { status: 400 });
  }
}

// ❌ Bad: Throwing plain errors
throw new Error("Invalid user");
```

### Performance

Follow performance best practices:

```typescript
// ✅ Good: Use memoization
const sortedUsers = useMemo(() => {
  return users.sort((a, b) => a.name.localeCompare(b.name));
}, [users]);

const UserCard = memo(function UserCard({ user }: { user: User }) {
  return <div>{user.name}</div>;
});

// ❌ Bad: Re-calculate on every render
const sortedUsers = users.sort((a, b) => a.name.localeCompare(b.name));
```

## Testing

### Testing Requirements

All contributions must include:

1. **Unit tests** for business logic
2. **Integration tests** for API routes
3. **E2E tests** for critical user flows

### Writing Tests

```typescript
// ✅ Good: Clear test names
describe("User API", () => {
  it("should return user by ID", async () => {
    const user = await getUserById("123");
    expect(user).toBeDefined();
    expect(user.id).toBe("123");
  });

  it("should return 404 for non-existent user", async () => {
    await expect(getUserById("999")).rejects.toThrow(NotFoundError);
  });
});

// ❌ Bad: Vague test names
it("works correctly", async () => {
  // ...
});
```

### Test Coverage

Maintain at least:

- **80%** code coverage for new features
- **100%** for critical business logic

```bash
# Generate coverage report
pnpm test:coverage
```

## Pull Request Process

### Before Submitting PR

1. **Sync with upstream**
   ```bash
   git fetch upstream
   git rebase upstream/main
````

2. **Run all checks**

   ```bash
   pnpm lint
   pnpm type-check
   pnpm test
   ```

3. **Build successfully**

   ```bash
   pnpm build
   ```

4. **Write good PR description**
   - What was changed
   - Why it was changed
   - How to test it

### PR Template

Use our [PR Template](../../.github/pull_request_template.md):

```markdown
## Description

Brief description of changes.

## Type of Change

- [ ] Bug fix
- [ ] New feature
- [ ] Breaking change
- [ ] Documentation update

## Related Issues

Closes #123
Related to #456

## Testing

- [ ] Unit tests added/updated
- [ ] Integration tests added/updated
- [ ] E2E tests added/updated
- [ ] Manual testing performed

## Checklist

- [ ] Code follows project style guidelines
- [ ] I have performed a self-review
- [ ] I have commented complex code
- [ ] I've updated documentation
- [ ] No new warnings generated
- [ ] Tests pass locally
- [ ] Accessibility considered (WCAG 2.2 AA)
```

### Review Process

1. **Automated checks**
   - CI/CD pipeline runs
   - Linting passes
   - Tests pass
   - Type checking passes

2. **Code review**
   - At least 1 approval required
   - Address all review comments
   - Update PR as needed

3. **Merge**
   - Rebase if needed
   - Squash commits (optional)
   - Delete branch after merge
